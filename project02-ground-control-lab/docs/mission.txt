RECOMMENDED ENVIRONMENT: Codex locally

1. ROLE AND MISSION

Act as a human-computer interaction and autonomy-assurance engineer building a scenario-driven ground-control alarm and handover interface laboratory.

Create a mock interface that helps a user determine the principal problem, related alarms, current control mode, pending handover, and entity responsible for the next action. Compare three purposeful interface designs against the same fictional incidents. Build an independent scenario truth model so displayed information can be checked for correctness and completeness. Demonstrate how the designs behave during alarm floods, stale information, conflicting reports, and interrupted handovers. Keep usability hypotheses separate from findings that require consenting human participants.

Controls must operate only the scenario engine, with no network link to aircraft, radios, flight software, or external services. Do not copy operational customer interfaces or controlled material. 5. FIRST COMPLETE MILESTONE

Implement ten scripted incidents and three designs: a conventional chronological alarm list, an incident-grouped view, and an explicit handover-state view. For each incident, specify the correct active issue, required information, permitted transitions, and completion conditions independently of the UI. Include stale telemetry, a secondary alarm cascade, conflicting acknowledgments, and an interrupted handover. Provide deterministic replay and export a correctness matrix showing which facts each design displays, obscures, or omits at defined scenario checkpoints.

6. IMPLEMENTATION SEQUENCE

1. Write scenario truth tables and a finite-state model for control ownership, acknowledgment, acceptance, cancellation, and timeout. Separate acknowledging an alarm from accepting responsibility.
2. Implement a local scenario engine with deterministic event playback, pause, rewind, and reset. Give every displayed status a timestamp and an explicit known, stale, or unknown state.
3. Build three interface variants using the same data model and event stream. Use text and structure in addition to color for severity, state, and responsibility.
4. Define task prompts such as identifying the responsible actor or locating the last reliable observation. Create an evaluator for factual correctness and required interaction steps.
5. Add keyboard navigation, screen-reader labels, readable focus indicators, and a reduced-motion presentation. Package a later optional participant protocol without conducting or inventing a study.

7. INDEPENDENT VERIFICATION

1. At each checkpoint, compare rendered facts with a separately authored scenario oracle. Test that stale data never silently appears as current and absent evidence never becomes an invented state.
2. Exercise simultaneous events, delayed acknowledgment, cancelled handover, and reset during replay. Verify that responsibility has an explicit state, including unresolved cases.
3. Run equivalent scenarios through all three designs and confirm identical underlying event order and timing so interface differences are not confounded by different information.
4. Complete the core tasks using keyboard-only interaction and inspect accessible labels and focus order. Check grayscale or color-deficiency views for lost meaning.
5. Plant a misleading alarm grouping and an incorrect ownership label, then require the correctness evaluation to detect both. Keep semantic findings separate from speculative human-factors benefits.
