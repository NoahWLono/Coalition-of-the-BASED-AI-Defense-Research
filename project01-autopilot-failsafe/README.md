# Project 1: Autopilot failsafe laboratory

This project is numbered 1 in the public portfolio. Historical experiment records and fictional redaction paths retain the original project 11 identifier.

This local laboratory records how two historical ArduCopter releases respond to simulated input failures during a stationary hover. It uses the official Linux SITL executables for ArduCopter 4.5.6 and 4.5.7 with the built-in quad model. The aircraft and site are fictional. The experiment is intended to exercise fault handling and evidence review; it does not establish aircraft flight safety.

The full experiment completed 58 real SITL runs across twelve fault scenarios and two pinned releases. Original corpus 1.0.0 produced 55 PASS, two expected disabled-failsafe failures, and one overly narrow text-assertion failure. A separate source-backed correction in corpus 1.0.1 passes retrospective replay of all four affected traces; the original failure remains preserved. Both versions reached the declared states within the tested deadlines. The [comparison report](docs/comparison.md) explains the evidence and limits.

Verification includes 41 passing unit tests, 522 passing provenance/isolation checks, the required independent onboard-log inspections, and two successfully detected wrong-mode replays. All twelve primary release pairs had 1,385 equal initial parameter values. No state-transition regression was observed within this configuration.

## Reproduce

From the portfolio root, run:

```bash
cd project01-autopilot-failsafe
bash scripts/reproduce.sh
```

The reproduction entry point prepares dependencies, runs the unit checks and current corpus 1.0.1 serially, evaluates saved traces, and writes JSON results. After a suite assertion failure, it still attempts summary, demonstration, trace-inspection and audit generation, then returns a nonzero exit status. It creates a new timestamped directory under `evidence/`; an optional first argument selects another output directory under this project's `evidence/`. It also writes a generated comparison, demonstrates the planted wrong-mode assertion, and cross-checks three selected onboard logs. The final comparison report is a separate reviewed interpretation of those results.

The supported host is Linux x86_64 with glibc, Bash, Python 3.9 or newer, `uv` 0.13.1, Bubblewrap, and the `timeout`, `ip`, and `ss` commands. Unprivileged user and network namespaces must work. The recorded host uses Bubblewrap 0.13.1. Bootstrap checks namespace availability before simulator execution; a failed isolation check stops the run. It never installs system packages or uses sudo.

To prepare dependencies without starting SITL:

```bash
bash scripts/bootstrap.sh
```

Bootstrap verifies the files listed in [manifest.json](manifest.json), prepares a project `.venv` with CPython 3.12.14, and installs `pymavlink` 2.4.49, `lxml` 6.1.3, and `fastcrc` 0.5.0 from pinned, hash-checked wheels. It uses a matching interpreter already present when available. Otherwise it downloads the pinned Python archive, then asks uv to install that verified local archive under `.bootstrap/python`. For a new environment, `LAB_BOOTSTRAP_LOCAL_PYTHON=1` selects this local fallback explicitly. The Python patch version is fixed; an existing interpreter can have a different build from the fallback archive.

All new dependency downloads and uv caches stay under `.bootstrap`; firmware downloads stay under `vendor`. Downloads use fixed HTTPS URLs, exact byte counts, and SHA-256 checks. A wrong cached checksum stops bootstrap and preserves the rejected file for inspection. Bootstrap allows at most 150 MiB of downloaded response bodies per invocation and has a 300-second wall limit. Once the required files are cached, bootstrap can run without network access. It does not change host network configuration or write to remote services.

## Experiment and isolation

GCS fault injection suppresses outgoing heartbeats while keeping telemetry available for observation; RC injection suppresses simulated receiver pulses.

The twelve cases cover persistent GCS loss, low battery, RC loss, restoration of each input, a brief GCS interruption, a brief battery dip, stale GPS input, and three combined failures. The complete plan has 58 simulator runs: two healthy baselines, all twelve cases on both releases, all cases repeated with a 0.7-second schedule offset, six selected repeats with a 1.4-second offset, and two disabled-GCS controls. Two additional offline replays demand a deliberately wrong mode. The [design](docs/design.md) records the initial expectations. Each sealed run retains its executed scenario. The JSON files in `scenarios/` specify current corpus 1.0.1; `scenarios/history/1.0.0/` preserves the original corpus. Its only corrected assertion permits both documented GCS status messages when battery and GCS failsafes occur together.

Each case starts with fresh persistent state. The controller must observe a healthy, armed GUIDED hover near 12 m before injecting a fault. Normal arming checks stay enabled. The location is a fixed fictional point at 0.01 degrees latitude and longitude, with a 0 m model elevation; no map service is contacted. The built-in simulator version is the corresponding autopilot commit. Its synthetic start-time origin is Unix 1700000000; event deadlines use elapsed simulator seconds. Schedule offsets are recorded, and no universal simulator random seed is claimed.

SITL runs in separate user, PID, IPC, UTS, and network namespaces with a private `/dev`, private `/tmp`, and a read-only host filesystem. Only the project directory is writable. The network namespace contains loopback and has no route to the LAN or Internet. The controller listens on `127.0.0.1:5760`, and SITL connects to it. The pinned SITL implementation also opens an RC UDP socket on `0.0.0.0:5501`. That wildcard socket is confined to the private namespace, where only loopback is available. Per-case socket and namespace records show what actually opened.

The published runner additionally sets the namespace hostname to `failsafe-lab` and overlays `/etc/machine-id` with `scripts/synthetic-machine-id`. This prevents future runs from recording the host identifiers found in the original logs. A namespace smoke check verified both fictional values, loopback-only networking, and an empty routing table. The historical suite predates this change; no fresh full simulator run with these publication settings is claimed.

The suite uses one SITL process at a time, speedup 4, two CPU affinity slots, and a 1.5 GiB address-space limit per simulator child. Each case has a 180-second outer wall limit. No hardware UART, radio, MAVProxy discovery, external dynamics service, or hardware bridge is configured. The built-in simulated GPS remains enabled on its internal serial channel.

The measured full stage took 31.7 minutes, followed by offline review. Allow about 35 minutes plus download and review time, and 1 GB of space for each new suite. The retained full evidence occupies about 589 MiB; development and starter evidence bring the total to about 647 MiB. Peak recorded simulator child RSS was 31.3 MiB. The suite checks its one-hour wall budget before starting each case; a case already running has its own timeout.

These are historical pins chosen for compatible behavior and available official binaries. They are not described as the newest releases. [The source review](docs/source-review.md) links the official manifests and records the relevant behavior. [The manifest](manifest.json) contains complete binary, configuration, dependency, and source snapshot hashes. `config/base-copter.parm` derives from the preserved upstream quad defaults with two unused airspeed parameters removed. `config/lab.parm` specifies the experimental thresholds and actions.

Each case saves received and transmitted MAVLink bytes, simulator and host timing, parameter readbacks, events, stdout, DataFlash logs, namespace details, and process cleanup status. Public copies use the redaction described above. SHA-256 publication seals protect those derivative files against unnoticed changes; the redaction report retains the original hash commitments. The offline evaluator reads these files separately from the controller and checks fault evidence before accepting a mode transition. Missing observations produce an indeterminate result. A LAND mode observation establishes a telemetry transition only.

The [trace contract](docs/trace-contract.md) defines files, clocks, and assertions. [Environment metadata](evidence/environment.json) records tool versions and resource totals without hostname, account name, hardware serial numbers, or network addresses.

ArduPilot is third-party software under the [upstream GPL license](docs/source-evidence/COPYING.txt). The official executables are fetched locally by bootstrap and excluded from version control. The selected source snapshots and license are retained for review; they are a subset of the full upstream source. The manifest links each executable to its official download and source commit. Python wheels are also fetched from their pinned upstream locations and excluded from version control.

## Review the retained experiment without rerunning SITL

From the project directory:

```sh
.venv/bin/python scripts/demo.py
.venv/bin/python scripts/audit_suite.py evidence/full
.venv/bin/python scripts/review_corpus_revision.py evidence/full
```

The [original machine results](evidence/full/comparison.json) intentionally retain `gates_resolved: false` for the corpus 1.0.0 text mismatch. The [revision assessment](evidence/full/corpus-revision-review.json) records `revised_corpus_gates_resolved: true` separately. All four affected traces pass the corrected text alternative. This is an assertion-only replay; no second full simulator execution of corpus 1.0.1 is claimed. A fresh clean-environment reproduction by a separate operator is the next concrete verification step.

To recompute the original results, run `PYTHONPATH=src .venv/bin/python scripts/summarize.py evidence/full --reevaluate` in Bash. Its exit code 1 is expected because it evaluates the sealed original scenarios, including the preserved text mismatch. Re-run the revision assessment afterward. The [trace contract](docs/trace-contract.md), [independent inspection](docs/trace-inspection.md), [compound ordering review](docs/compound-ordering-review.md), and [review record](docs/review-record.md) explain how conclusions were checked.
