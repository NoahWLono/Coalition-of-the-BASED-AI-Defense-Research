5. FIRST COMPLETE MILESTONE

Complete twelve documented fault scenarios and a comparison between two compatible pinned releases. Begin with three complete scenarios on the first release to establish the harness, then expand without treating that starter demonstration as completion of the full milestone. Cover link interruption, a battery-related threshold, stale sensor data, recovery, and selected simultaneous faults that the simulator can express reliably. For each scenario, record initial state, fault timing, expected allowed states, a justified response deadline, observed transitions, and a deterministic outcome. Publish one command that reproduces the executed suite from a clean project environment.

6. IMPLEMENTATION SEQUENCE

1. Inventory available simulator support and dependencies, choose the smallest documented headless setup, and record the autopilot commit, simulator version, parameter file, timing model, and resource budget.
2. Write a declarative scenario format with preconditions, fault events, expected transitions, permitted alternatives, deadlines, and cleanup behavior. Keep expectations outside the fault-injection implementation.
3. Implement a runner that creates an isolated instance, checks starting conditions, injects only supported software faults, records monotonic host timing and simulator timing separately, and always tears down the instance.
4. Write a separate evaluator that reads immutable simulator logs and checks state, ordering, and deadline assertions. Preserve raw evidence for unexpected or indeterminate results.
5. Compare two pinned versions with equivalent configurations where possible. Document semantic or parameter changes that prevent a fair comparison instead of silently translating them.

7. INDEPENDENT VERIFICATION

1. Confirm the baseline completes before injecting failures, and verify from logs that the intended fault actually occurred. A passing assertion without a confirmed injected fault does not count.
2. Manually inspect at least three representative traces using an independent log reader or documented field definitions, including one recovery path and one compound failure.
3. Run negative controls with a deliberately disabled relevant failsafe or an intentionally wrong expected transition, and require the evaluator to detect the corresponding mismatch.
4. Repeat timing-sensitive scenarios across multiple seeds or schedules. Distinguish nondeterminism, wall-clock resource contention, missing observations, and genuine state-transition differences.
5. Check that instance ports bind locally and no hardware bridge is enabled. Verify the full run leaves no simulator process, altered host network rule, or active device connection.
